How AgentManager stores and routes agent processes

One workspace owns one sandbox VM. Inside that VM, HarnessBox can run many long-lived agent CLI processes — one per conversation. This doc explains the identity model, persistence, and the exact path from an HTTP prompt to the correct stdin of the right process.

Internal only. Not part of the public OKF bundle under docs/. Aimed at engineers wiring the dashboard, CLI, or multi-conversation UX.

Overview

HarnessBox separates local durable project/workspace/session metadata from cloud compute (the sandbox) and agent chat state (conversations and CLI processes). A provider sandbox id is only how we reconnect a runtime. Agent routing never uses a provider sandbox id, branch, or worktree path as a chat key. 

Project (local repository record)
  └─ Workspace (workspace_id) ────────────────────────┐
     │  SQLite: project + workspace rows               │
     │  In-memory: WorkspaceInstance                  │
     │                                                │
     ├─ Sandbox (provider_sandbox_id)  ← cloud runtime │
  │     filesystem, network, PIDs                      │
  │                                                    │
     └─ AgentManager                                  │
           ├─ conversation A → AgentProcess (harness) │
           ├─ conversation B → AgentProcess (harness) │
           └─ conversation C → AgentProcess (harness) │
                 ↑ keyed only by conversation_id      ┘

Concurrency contract

Many conversations, one intentionally shared workspace

Different conversations in the same workspace are intended to execute in parallel. Their agent processes share the same sandbox, checkout, branch, filesystem, network namespace, and installed tools.

HarnessBox serializes turns within a single conversation. It does not serialize, isolate, detect, or reconcile file edits and Git operations across different conversations. Callers choose when parallel work is appropriate and own any resulting coordination or conflicts.

Workspace lifecycle operations are a separate concern. Connect, pause, snapshot, recovery, and destruction must coordinate safely with active turns, but lifecycle locking must not become an implicit single-writer policy for ordinary conversation turns.

Implementation note. Turns are serialized per conversation by AgentManager; workspace lifecycle coordination is separate and is not held across the full streamed turn.

Identity layers

ID Owned by Purpose
workspace_id HarnessBox server (minted) Primary HTTP resource. Selects sandbox + AgentManager.
provider_sandbox_id E2B Pause/resume/connect the VM. Not sent by clients on prompt.
conversation_id HarnessBox (UUID) Stable chat thread. Keys the in-memory AgentProcess map.
agent_type Stored per conversation Harness name: claude-code, codex, …
agent_session_id Agent CLI (e.g. Claude) Native session id for --resume after process death.
event session_id Streaming layer Normalized to conversation_id before clients see it.

Components

WorkspaceManager

Facade: registry + idle + session router + event replay. HTTP handlers call this.

WorkspaceRegistry

In-memory map of WorkspaceInstance. Owns create/hydrate/pause/resume and attaches one AgentManager per live sandbox.

SessionRouter

Prompt path: resolve conversation, upload attachments, call AgentManager.send_message, persist events and agent_session_id.

AgentManager

Per-workspace process table: conversation_id → AgentProcess, with per-conversation locks. Lazy spawn; reuse across turns.

AgentProcess

Long-lived CLI in the sandbox. JSON-line stdin prompts; NDJSON stdout; stays up between turns.

StorageBackend

SQLite (default) or memory. Durable workspace + conversation metadata + event history. Not the live process table.

What is stored where

In memory (lost on server restart until hydrate)

  • WorkspaceInstance.sandbox_conn — live Sandbox / provider handle
  • WorkspaceInstance.agent_manager — the process map
  • AgentManager._agents — dict[conversation_id, AgentProcess]
  • AgentManager._locks — serializes turns per conversation
  • Sandbox EventBuffer — recent events for SSE replay

Durable (SQLite ~/.harnessbox/sessions.db by default)

conversations table (core columns):

conversation_id   TEXT PRIMARY KEY
workspace_id      TEXT  → workspaces
agent_type        TEXT  NOT NULL   -- harness for this conversation
title             TEXT
last_active       TEXT  NOT NULL
agent_session_id  TEXT              -- CLI --resume id (migration v005)

Active conversation is not a separate flag. It is defined as the row with the latest last_active for that workspace (ORDER BY last_active DESC LIMIT 1).

Events are stored under workspace_id (not conversation), with conversation context inside event JSON / metadata. Conversation rows carry the routing metadata needed to respawn the right harness.

Important split

Storage remembers which conversation / harness / Claude session. The running PID and stdin pipes live only in AgentManager. After pause or process death, the next prompt respawns from storage metadata — it does not revive the old Python object.

Request routing (prompt path)

Endpoint: POST /v1/workspaces/{workspace_id}/prompt
Body: { prompt, harness, conversation_id?, attachments? }

1
Select workspace Path workspace_id → WorkspaceRegistry.get_workspace. Wrong id → 404. This is the only required client identity today.
2
Ensure sandbox ensure_sandbox resumes the provider runtime if paused (via provider_sandbox_id stored on the workspace). Still no agent routing — just compute.
3
Resolve conversation SessionRouter._resolve_conversation:
  • If client sent conversation_id → load that row; use its agent_type and agent_session_id (stored harness overrides body harness).
  • If omitted → take active conversation (latest last_active), or mint a new UUID.
4
Delegate to AgentManager info.agent_manager.send_message(conversation_id, prompt, harness, agent_session_id=…). Lookup / spawn process keyed by conversation id.
5
Stream + persist Events pushed to the sandbox event buffer and SQLite. Claude’s native session id is captured from stream metadata into _agent_session_id, then written back to the conversation row at turn end.

Lazy spawn

if conversation_id not in self._agents:
    await self._spawn_agent(conversation_id, harness, agent_session_id=…)

async with self._locks[conversation_id]:
    process = self._agents[conversation_id]
    await process.send_prompt(prompt)
    async for event in process.stream_turn():
        # rewrite event.session_id → conversation_id
        # stash CLI session id in metadata["_agent_session_id"]
        yield event

Spawn command

get_harness_type(harness).build_session_command(…, session_id=agent_session_id) builds the CLI argv. If agent_session_id is set, the harness typically includes --resume <id> so Claude (or peers) restore history even though the OS process is new.

Concurrency

  • Required invariant: turns for the same conversation are serialized by its asyncio lock.
  • Required behavior: turns for different conversations may execute concurrently, even though they share one filesystem and Git working tree.
  • User responsibility: HarnessBox does not prevent or merge cross-conversation file and Git conflicts.
  • Current gap: workspace-level locking in SessionRouter.prompt wraps the whole turn, so prompts are effectively serialized per workspace until that lock is narrowed.

Session id rewriting

The CLI may emit its own session id on events. AgentManager rewrites event.session_id to the HarnessBox conversation_id so clients see a stable thread id, while preserving the CLI id in metadata for persistence.

Multi-harness / multi-conversation

Server support is already there. Pattern:

# Conversation A — Claude on shared sandbox
POST /v1/workspaces/ws_1/prompt
{ "prompt": "…", "harness": "claude-code", "conversation_id": "conv_a" }

# Conversation B — Codex on the SAME workspace/sandbox
POST /v1/workspaces/ws_1/prompt
{ "prompt": "…", "harness": "codex", "conversation_id": "conv_b" }

Resulting AgentManager map:

_agents = {
  "conv_a": AgentProcess(claude-code …),
  "conv_b": AgentProcess(codex …),
}

Both processes share the same filesystem and network namespace of the sandbox. They do not share chat history — that is per CLI session / conversation.

They may run at the same time. This is intentional: one conversation may explore the codebase while another implements an unrelated task on the shared branch. If parallel agents edit overlapping files or manipulate the same Git state, HarnessBox does not arbitrate the conflict.

Harness stickiness

Once a conversation row exists, _resolve_conversation prefers stored agent_type over a mismatched harness in the request body. To switch harnesses, mint a new conversation_id (new thread), do not reuse the old one with a different harness name.

Pause, resume, and recovery

Lifecycle coordination must account for all active conversation turns. Idle pause begins only when none are active. Explicit pause, snapshot, and destroy operations need bounded wait/cancel semantics; they must not rely on whole-turn workspace serialization as a substitute for lifecycle coordination.

  1. Pause workspace — may snapshot; then E2B pause(); store provider_sandbox_id; runtime → PAUSED.
  2. Resume — Sandbox.connect(provider_sandbox_id) (plus egress probe). On successful in-place resume, registry typically agent_manager.shutdown_all() rather than reattaching stale stdout pipes.
  3. Next prompt — resolves conversation → loads agent_session_id → AgentManager spawns a fresh process with --resume.
  4. Expired sandbox — recover from filesystem snapshot if available; new VM + same conversation recovery path via stored ids.

reattach_all() exists for reconnecting stdout after resume, but the current pause/resume happy path prefers shutdown + respawn for reliability (Claude’s outbound HTTP can go stale across pause).

Client contract today

Client Sends Effect
Web dashboard workspace_id in URL; body { prompt, harness } only Always hits active conversation (or creates one). Multi-conversation UI not wired.
