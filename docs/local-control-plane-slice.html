1. The Problem

HarnessBox manages AI coding agent sessions that run inside cloud sandboxes (E2B VMs). These sessions can be paused (VM suspended) and resumed (VM reconnected) across server restarts, idle timeouts, or manual user action. The SSE (Server-Sent Events) stream delivers events to connected clients in real-time.

Before this change, five critical flaws existed in the pause/resume lifecycle:

Flaw 1: Event Sequence Gaps

When a workspace was paused and resumed, the EventBuffer started fresh with sequence=0. Clients reconnecting with a Last-Event-ID would receive events with duplicate or conflicting sequence numbers, causing timeline corruption in the UI.

Flaw 2: Buffered Event Loss on Pause

The EventBuffer batches events for persistence (50 events or 5 seconds). If a pause happened mid-batch, pending events were silently lost. The flush task was never guaranteed to run before the VM suspended.

Flaw 3: Eager Sandbox Instantiation

_hydrate_workspace() eagerly created a Sandbox object and AgentManager for every workspace loaded from storage, even those that might never be resumed. This wasted resources and could trigger invalid state transitions (e.g., STARTING -> PAUSED).

Flaw 4: SQLite Concurrency Corruption

Read operations (get_workspace, list_workspaces, get_events) ran without any lock, while writes used _write_lock. Under concurrent access from asyncio.to_thread(), this caused cursor corruption and "database is locked" errors.

Flaw 5: Empty Ring Buffer on Reconnect

After resume, the in-memory ring buffer was empty. SSE clients sending Last-Event-ID: 42 would get zero replay events, even though events 1-42 existed in the database. The timeline showed a gap until new events arrived.

2. What We Implemented

Four coordinated changes that together guarantee gapless, monotonically increasing event sequences across any number of pause/resume cycles:

A. Storage: get_max_sequence

New protocol method that returns the highest event sequence number for a workspace. Used on reconnect to seed the EventBuffer so new events continue from the correct point.

B. Events: hydrate()

New method on EventBuffer that loads up to 1024 recent events from storage into the ring buffer. Enables instant replay for reconnecting SSE clients.

C. Lifecycle: Guaranteed Flush

SandboxSession.pause() and kill() now call event_buffer.close() before suspending the VM. Zero buffered events can be lost.

D. Orchestration: Lazy Hydration

_hydrate_workspace() no longer instantiates Sandbox/AgentManager. Connection is deferred to the lock-protected _connect_sandbox() path, called lazily on first prompt.

3. Architecture Changes

Before: Eager Hydration with Sequence Reset

Server Start -> load_workspaces() -> _hydrate_workspace() // Creates Sandbox + AgentManager eagerly -> WorkspaceInstance(sandbox_conn=Sandbox(...), agent_manager=AgentManager(...)) First Prompt -> _ensure_sandbox() -> resume(provider_sandbox_id) -> EventBuffer(initial_sequence=0) // WRONG: starts at 0, duplicates stored sequences

After: Lazy Hydration with Sequence Continuation

Server Start -> load_workspaces() -> _hydrate_workspace() // Returns sandbox_conn=None, agent_manager=None -> WorkspaceInstance(sandbox_conn=None, agent_manager=None) // Lightweight record only First Prompt -> _ensure_sandbox() // sandbox_conn is None, triggers connect -> _connect_sandbox() // Under asyncio.Lock | max_seq = storage.get_max_sequence(workspace_id) // e.g. returns 42 | Sandbox(..., initial_sequence=42) // EventBuffer starts at 42 | sandbox.resume(provider_sandbox_id) | sandbox.event_buffer.hydrate() // Ring filled from DB: events 1-42 available for replay -> AgentManager(sandbox) -> info.sandbox_conn = sandbox // Now connected New Event Pushed -> EventBuffer.push() // sequence becomes 43, 44, 45...

Pause Flow (Guaranteed Flush)

pause() -> transition(PAUSED) -> event_buffer.close() // Cancels flush task, forces final flush | // All pending events written to SQLite | // Subscribers notified with None (stream ends) -> provider.pause() // VM suspends ONLY after flush completes

5. Data Flow: Event Lifecycle

Event Creation to Persistence to Replay

// 1. Agent emits raw NDJSON
StreamParser.parse_line(ndjson) -> UniversalEvent(sequence=0)

// 2. EventBuffer assigns authoritative sequence
event = await event_buffer.push(raw_event)
// event.sequence is now 43 (previous was 42)

// 3. Broadcast to live SSE subscribers
for queue in subscribers:
    queue.put_nowait(event)

// 4. Batch persistence (50 events or 5 seconds)
_pending.append(event)
if len(_pending) >= 50:
    await storage.append_events(session_id, batch)

// 5. On pause: guaranteed flush
await event_buffer.close()  // Forces all pending to DB

// 6. On resume: hydrate ring from DB
max_seq = await storage.get_max_sequence(workspace_id)  // 43
buffer = EventBuffer(initial_sequence=max_seq)
await buffer.hydrate()  // Ring now has events 1-43

// 7. Client reconnects with Last-Event-ID: 40
replay = buffer.replay(after_sequence=40)  // Returns events 41, 42, 43
// Then live events 44, 45... stream normally

6. Recommended Usage and Applications

For SDK Users (Library Consumers)

No API changes required

These changes are internal to the SDK's lifecycle management. If you're using Sandbox directly or through WorkspaceManager, the behavior is automatically improved. The only new public surface is:

  • Sandbox(..., initial_sequence=N) — optional param, defaults to 0 (backwards compatible)
  • EventBuffer.hydrate() — called internally by WorkspaceManager, but available for custom orchestration
  • StorageBackend.get_max_sequence(workspace_id) — must be implemented by custom storage backends

Custom Storage Backend Implementors

Breaking Change for Custom Backends

If you have implemented the StorageBackend protocol with a custom class (e.g., Supabase, PostgreSQL), you must add this method:

async def get_max_sequence(self, workspace_id: str) -> int:
    """Return the highest event sequence for a workspace, or 0."""
    # Example for PostgreSQL:
    row = await self.pool.fetchrow(
        "SELECT COALESCE(MAX(sequence), 0) FROM events WHERE workspace_id = $1",
        workspace_id,
    )
    return row[0]

Application: Real-Time Dashboard

The HarnessBox web app (planned) will show a live event timeline per workspace. This change ensures:

  • The timeline never has gaps when a user navigates away and returns
  • Multiple browser tabs can subscribe and replay independently
  • Historical events are browsable even after workspace pause/resume cycles
  • The Last-Event-ID HTTP header (SSE standard) works correctly for automatic reconnection

7. Benefits and Trade-offs

Benefits

  • Zero event loss: Guaranteed flush before any lifecycle transition prevents silent data loss
  • Gapless replay: Clients reconnecting after pause/resume get a complete timeline
  • Correct sequence ordering: No duplicate or conflicting sequence numbers across cycles
  • Lower memory at boot: 100 paused workspaces no longer require 100 Sandbox instances in memory
  • SQLite reliability: Serialized access + WAL + busy_timeout eliminates concurrency bugs
  • Backwards compatible: initial_sequence=0 default preserves existing one-shot behavior

Trade-offs

  • Slightly slower resume: _connect_sandbox() now does one extra query (get_max_sequence) + hydration read. Cost: ~1-5ms for SQLite, negligible vs. VM resume time (~2-5s)
  • Serialized SQLite reads: All reads now acquire _lock. Under high concurrency (50+ parallel reads), throughput may be constrained. In practice, HarnessBox workspaces are 1-3 concurrent conversations, well below this threshold
  • Hydration memory: hydrate() loads up to 1024 events into the ring buffer. At ~2KB per serialized event, this is ~2MB peak per workspace. Acceptable for a local control plane
  • Protocol break for custom backends: Any custom StorageBackend implementation must add get_max_sequence() or it will fail at runtime
  • Pause is slightly slower: close() on the event buffer flushes pending events synchronously before VM suspend. If there are 49 pending events, this adds one DB write (~1-3ms)
